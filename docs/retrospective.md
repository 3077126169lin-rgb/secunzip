# 复盘

本文是一次事后复盘，材料来源是本仓库的代码、文档与提交历史，不含未记录的推测。凡是数字都取自 [CHANGELOG.md](../CHANGELOG.md)、[README.md](../README.md) 与 [docs/design.md](design.md) 的现存文本。

## 1. 初衷与最终形态

最初的设想是一套完整的受控内容分发体系：密钥由服务端托管，打包时用机器码、系统日期、本机 IP、域用户构造派生流程，接收方在**自己的机器上**重新求值才能解开；配以内存只读挂载、沙箱执行、黑盒 EXE 与客户端可设的有效期。设计文档里的能力清单曾经长得多。

实际交付的是一个明显更小的东西。README 的「实现状态」表逐条对照后有 13 项：6 项标注已实现、3 项部分实现、4 项未实现（其中 IP 白名单在审计之后转为服务端强制，因此「已实现」那一侧比审计当时厚了一点，装饰性字段那一侧则薄了一点）。真正立得住的核心链路只有一条：

```
pack（归档为 ZIP 后整体加密）→ 服务端 register 登记与 grant 授权 → 接收方联网取 content_key
→ 内存解密为只读 VirtualFS → 回环 WebDAV 映射为盘符浏览
```

这条链路是端到端跑通过的，其余部分则有相当比例停在文档与注释里。

更彻底的信号在配置结构里：`PackConfig` 有 11 个序列化字段，其中 5 个（`hash`、`run_mode`、`ip_whitelist`、`app_id`、`allow_temp`）在审计时是零读取、或读的根本不是该字段；`RunMode`、`AuthMode`、`CryptoAlgo`、`HashAlgo`、`CompressAlgo` 五个枚举里各有一部分变体，唯一作用是保持头部编码稳定。界面上能选的算法远多于能跑的算法，能设的开关远多于会被读的开关。

测试数量是这条分界线的旁证：0.1.0 是 73 个，0.1.1 增至 82 个，0.1.3 增至 103 个（核心库与 CLI 73、服务端 30，后者为 3 个单元加 27 个集成）。增长主要发生在服务端——因为服务端**一度是 0 个自动化测试**，而它恰恰是全部安全逻辑所在。提交历史 55 条，全部落在 2026-09-28 一天，v0.1.0 至 v0.1.3 四个 tag。这个密度本身就解释了后面大多数缺陷：能力是自下而上堆起来的，不是照着一条验收链路装起来的。

## 2. 站得住的设计

**核心链路选对了。** 打包产物是「明文头 + 加密体」，密钥由服务端托管、打开时联网获取，这条主线上没有一处分叉；CLI 与 GUI 走的是同一套加载器与同一个 VFS，不存在两套语义。

**信任边界划在服务端，这是整个项目最重要的一个正确决定。** 客户端在接收方手里，可以被反编译、替换、打补丁；因此任何只在客户端执行的检查都不构成约束。以服务端为唯一信任锚之后，`revoke` 的意义、`content_key` 不写入产物头部、Remote 模式下清空头部 `key_derive` 字段这些设计才有统一的解释。IP 白名单最终也是按这个原则收口的：从「写进产物头部、没有任何代码读它」改成 `/api/key` 按 TCP 连接的对端地址在服务端校验（`apps.ip_whitelist` 列，schema 升至 v2），管理员不豁免。[docs/design.md](design.md) §7 同时如实记录了它的效力边界——服务端经 TCP 转发或反向代理接入时，它看到的是代理地址，实测为 Docker 网桥网关 `172.17.0.1` 而非客户端真实地址，那种拓扑下白名单会拦下所有人。能把自己的防线说清楚到什么程度，比防线本身更少见。

**一切都是从「服务端持有的那一个密钥」派生出来的**，而不是分散的客户端校验；这让「把某台机器上的客户端黑掉」不能换来解密能力。

**边界划对之后，修改是不对称的。** IP 白名单从「头部字段」改成「服务端强制」时，只需改服务端加一次 schema 迁移，客户端一份产物格式都不用动；头部那个字段按 bincode 兼容性保留即可，旧产物继续可解析。反过来，如果把校验放在客户端，任何加固都要等接收方升级——而接收方正是对手。这条不对称性是第 5 节那条「执行点放在对手改不动的一侧」的经验来源。

**接受的取舍被写下来了，而不是消失在讨论里。** 明文 HTTP 传输、文件 ID 用 MD5、`secret` 比较非恒定时间、服务端无速率限制、文件头无 MAC——这些都在 [SECURITY.md](../SECURITY.md) 里逐条列为「已知且接受的风险」，并说明各自缓解（密文有 GCM tag 保护、篡改明文头会改变文件 ID 从而查不到 ID、对外必须前置 TLS 反向代理）。一个课程项目能把自己的弱点列成清单而不是藏起来，比多实现一个算法更难得。

**明文不落盘是写进目标并有条件做到的。** 默认路径是内存 VFS，只有显式 `open -o <目录>` 才解压到磁盘；挂载是回环地址上的只读 WebDAV，不产生中间明文文件。「有条件」是诚实的措辞：`execute_sandbox` 与 `Executor` 两条执行 EXE 的路径都会先写临时目录（[docs/design.md](design.md) §3.3 已注明），属于「不承诺覆盖全部路径」，而不是承诺了没做到。

**零运行时依赖。** 三个可执行文件都是自包含的原生二进制：SQLite 以 `bundled` 编译进服务端，Windows 侧只依赖系统 DLL、不需要 VC++ Redistributable，Linux 服务端另有 musl 静态链接产物。这条约束反过来救过设计——真正的内存文件系统挂载需要 WinFsp / Dokan 之类的驱动，与零运行库依赖直接冲突，于是 ISO 方案被否决，而不是被半途实现。

**把有杀软风险的能力按在门外，是主动决定而非疏忽。** 内存 EXE 执行（RunPE）由 `Cargo.toml` 的 `runpe` feature 门控、默认不编译，`run_pe_memory` 全程零调用点。README 的实现状态表把它列为未实现，设计文档的路线图把它列为未完成而不是已完成。写了一段演示不了的能力却不敢打开它，正确的处置就是让它保持关闭并在文档里说清楚。

**文档诚实化本身被当成一次交付。** 0.1.2 是「文档诚实化，代码零改动」——新增实现状态表、订正 [docs/design.md](design.md) 与 [docs/technical.md](technical.md) 中与实现不符的描述。它没有修任何功能，但把「读者会被文档误导」这个缺陷类型从工程里单独摘了出来。

## 3. 成了纸面的设计

**环境指纹绑定：号称的核心卖点，实为打包机上求值一次的常量。** 这是全部声明与实现之间最大的缺口。密钥派生流程（`KeyNode` 树）确实有完整实现、有测试、在 GUI 里有可视化的构造入口，但整棵树只在**打包侧求值一次**，结果转成一个十六进制字符串即 `content_key`，交给服务端托管；打开时客户端固定按 `KeyNode::Input(KeySource::Literal(服务端下发的字符串))` 重建密钥。于是 `MachineGuid`、`CurrentDate`、`LocalIp`、`DomainUser` 这些来源只在打包机上被读一次——**接收方的机器码、系统日期、IP、用户名在打开时从未被读取**。「密钥取决于接收方环境」在代码里不成立。

更值得记住的是这个失败**不可修复**：即便把打开路径接上也没有意义，接收方控制客户端，指纹可以伪造。真正可行的只有服务端侧的注册式绑定（接收方先交指纹给管理员）或短期/一次性密钥，两者都只是延后与收窄，不是阻止。这个结论连同代价写在 [docs/design.md](design.md) §9，比接一条假的客户端校验有价值得多。

**`RunMode` 的三个模式不携带任何行为。** 字段被 bincode 写进每个产物的文件头，全仓库只有构造点与字段声明，没有一处读取，`RunMode::Document` 变体零引用。它的价值只剩「保持头部编码稳定」，变体顺序都不能改，否则旧产物会解析错位。留在枚举里的语义其实是**现状的别名**：默认行为即 `Document`，`-o` 即 `TempDir`，`Sandbox` 对应未接入的 RunPE——所以正确处置不是写新分支，而是把命名对齐到实现。

**ISO 挂载：被否决，而不是没写完。** 设计文档曾把「文档模式 = ISO 挂载」写进注释，实现从来不存在，而且它不会被补上：Windows 的 `Mount-DiskImage` 只能挂载磁盘上**真实存在**的镜像文件，满足它就必须先把解密后的明文写成 `.iso` 落盘，直接推翻「明文不落盘」这一核心目标；纯内存挂载则要依赖 WinFsp / Dokan 或已签名的内核 minifilter，既超出课程项目的现实，也违背零运行库依赖。把「考虑后否决的替代方案与理由」留档，比删掉这段描述更有用——它阻止后来者重新走一遍同一条死路。

**IP 白名单：写进产物头部，无人读取，且即使读了也无意义。** `PackConfig.ip_whitelist` 全仓库只有构造点，从未参与校验；而客户端校验本身就是无意义的，因为接收方掌握客户端二进制。该字段最终按 bincode 头部兼容性要求保留，但执行者移到服务端——它现在是一个有明确标注的「保留但已不是执行者」的字段。

**黑盒自解压 EXE：机制是完整的，只开了一扇门。** runner 取的是打包进程自身的 `current_exe()`，打开时自查尾部标记，这条路本身成立；但 CLI 入口没有尾部标记检测、`pack` 也没有 blackbox 开关、`cmd_pack` 恒传 `false`，于是**只有「用 GUI 打包 + 双击产物」**这一条路可能成立。这是未完成的接线工作，而非设计缺陷——后来 CLI 补上 `pack --blackbox` 与启动时的尾部自查（先只读末尾 16 字节做廉价预判），两个入口就都能产出和双击了。它也是最好的例子：**「像纸面能力」和「像未完成接线」的缺陷修法完全不同**，而复盘的价值之一就在于分清这两类。

**客户端够不到的开关。** `AuthMode::Local` 在 `open` 处直接报错拒绝，且没有任何生产者会生成 `Local` 产物；文件内 `expire_at` 的读方存在（加载器里的过期检查）但打包侧恒为 `None`、无 CLI 开关可设，检查永不触发。两者都不是错误，而是「客户端不可达」：Remote 模式下服务端的授权有效期已经完整工作（授权、审批、过期拒绝与清理），文件内有效期对当前唯一可用的模式是冗余的。结论写进了 [docs/design.md](design.md) §9：要用文件内过期，前提是先接上离线模式。

## 4. 缺陷的类型学

记录在案的 16 条缺陷（13 条工程/测试/运维 + 3 条由使用者从操作视角发现），按失效方式归并后只有六类。按类读，比按时间读更能带走东西。那 3 条使用者发现的缺陷分别是：默认盘符被硬编码成 `Z:` 且卸载会删掉用户自己的映射、设计文档把「打开文件」描述成挂载只读 ISO、以及界面上一次假的挂载成功。它们的共同点是「设计者以为的行为」与「用户实际看到的行为」之间的差距，没有一条是单元测试能抓到的——**用户视角的缺陷报告比测试通过更有信息量**。

**（一）纯接线遗漏：能力是完整的，只是没人接。** 黑盒 EXE 缺 CLI 开关是典型；`run_pe_memory` 有完整实现但零调用点、`Executor` 整体无调用点是另一种——代码写完了、测试没写、入口没开。这类缺陷的共同点是：**任何只读代码的评审都会认为它已经完成**，因为实现确实在里面。检验手段只有一个：从入口出发做一次可达性检查，问「这个函数在生产构建里到底会不会被执行」。

**（二）文档漂移：文档描述的是意图，代码做的是另一件事。** 这是本项目**数量最多的一类**，也最危险，因为它不会让程序出错，只会让评审者得出错误结论。实例：`API.md` 声称注册了 `GET /`（实际是客户端探测根路径并接受任意 HTTP 响应，服务端并未注册该路由，后来改为 `GET /healthz` 并澄清了客户端的真实行为）；`execute_sandbox` 的注释写「沙箱模式执行（内存）」，实际是写临时目录再调资源管理器打开；设计文档声称文档模式是 ISO 挂载；`deploy/README.md` 让读者去执行两个由安装脚本生成、并不在仓库里的 service 脚本；以及最刺眼的一条——设计文档的路线图把「RunPE 内存执行」标成 `[x]` 已完成。共同规律：**漂移总是朝着「项目更强」的方向发生**，作者写文档时写的是自己将要做的，之后没有再回来把 `[ ]` 改回去。处置方式后来固定为：以代码为准逐条订正，无法确认的标「未确认」，结论不软化。

一个容易忽略的细节是：缺陷 3 查清之后，代码一行都没改。客户端的连通性探测确实能工作，只是服务端没有对应路由，原来的文档把「客户端请求了什么」和「服务端注册了什么」混成了一句话。**文档缺陷与代码缺陷需要分开处置**——在这里，正确的修法是改文档，而不是为了对齐文档去加一个没人调用的路由。

**（三）静默降级：错误被吞掉，用户拿到一个看起来正常的东西。** 三个压缩算法（`SevenZ`、`TarZst`、`TarGz`）打包时静默按 ZIP 处理，用户以为拿到 7z 实际得到 ZIP；`KeyTransform::Concat` 是个原样返回的空操作，调用方以为拼接发生了；`net use Z: ...` 的退出码被 `let _ = ... .output()` 丢掉，盘符被占用导致映射失败时界面照样弹「已挂载到 Z:」，随后点「卸载」无条件执行 `net use Z: /delete /y` 把用户自己的映射删掉。这一类里最坏的不是功能缺失，而是**后续动作建立在假成功之上**。它后来被整体改为失败即报错：未实现的算法返回明确的中文错误而非 `unimplemented!()` panic，压缩算法不再回退为 ZIP，相关工厂去掉 `_ =>` 兜底改为穷尽匹配——让新增变体在编译期就被迫处理。

**（四）注释与死代码冒充实现。** 与（二）相邻但不同：不是文档落伍，而是**注释或未编译的文件被当成了实现**。`src/runtime/stub.rs` 整个文件没有被声明为模块、不参与编译，却是本地解密路径唯一的调用点，于是「本地解密在已发布二进制里不可达」这件事在很长时间里看不出来；`ProjectConfig` 全仓库零引用；`RunMode::Document` 的语义只存在于注释。处置是把死代码删除，而不是给它补文档——留着它就等于留着一个未来的错误答案。

**（五）验证方法本身出错，且伪装成功能故障。** 这类只出现过两次，但两次都值得单独记住。`v0.1.1` 发布后用主发布页的静态 HTML 判断产物数量，结果一直是 0，排查了近 30 分钟——原因是 GitHub 的发布页**懒加载**产物列表，静态 HTML 里根本没有下载链接，产物其实已经上传完毕。第二次是服务端测试 `test_port_in_use_exits_with_error`：它先绑定 `127.0.0.1:P`，再期望服务端绑 `0.0.0.0:P` 失败；但在 Windows 上后者**依然成功**，服务端不退出，`Command::output()` 于是无限等待，因为输出被管道过滤，现场只表现为「命令很久不返回」，一度被误判为 cargo 抢锁与联网超时，最终被归因为「构建很慢」。两个案例的教益相同：**先验证检测手段，再相信它的结论**。前者只要拿 `v0.1.0` 做一次对照就能立刻发现；后者只要问一句「这个断言在什么条件下会失败」就会发现它永远不会失败。

**（六）运维自伤：工具的作用对象包含了操作者自己。** 在容器内用 `pkill -f '/config/secunzip/secunzip-server'` 停服务时，`docker exec` 下 pkill 自身的命令行也包含这个模式，它把自己一起送掉了；更要紧的是看护循环被终止后服务不再自愈，容器内 8090 变成无人监听。恢复是重新执行 init 脚本（它自带 already running 检查，重复执行安全）。同一事故还暴露出更深的一层：那个 `while true` 看护循环**本身不保证存活**——重启自启有效（走 init 钩子），进程崩溃后的自动恢复不可靠，正确做法是注册成 s6 服务、由 s6 做真正的进程监督，而不是依赖 init 钩子里的后台循环。这一条写进了记录但没有实施，因为该容器还跑着使用者的桌面环境、需要重启才生效；**未解决的遗留问题被明确标记为未解决，比假装它不存在有价值。**

## 5. 如果重来会怎么改

**先定安全边界，再删掉边界之外的一切。** 边界是服务端。凡是无法在服务端强制执行、只能由客户端自证的策略，一律不做——不是「先做客户端版以后再搬到服务端」，而是从一开始就不写。按这条规则，头部 `ip_whitelist`、`run_mode`、`app_id`、`hash` 这些字段根本不会被设计出来。

**序列化的配置字段必须有一个消费者。** 允许保留，但必须显式标注「保留，无执行者」并说明保留原因（bincode 兼容 / 预留语义）。测试断言「字段能往返序列化」不算消费者，它只证明写进去了。

**未实现的枚举变体必须响亮地失败。** 不要落到 `_ =>` 兜底分支、不要 `unimplemented!()` 在运行期才炸、更不要静默替换成另一个算法。让工厂做穷尽匹配，把代价推到编译期；确实未实现的返回带名字的中文错误。

**验收测试写在功能之前。** 本项目最终补上的 `tests/robustness_test.rs`、`tests/algorithm_test.rs`、`tests/cli_blackbox_test.rs` 与 27 个服务端黑盒集成测试，每一个都是「让程序回答『它到底能不能用』」，而不是靠人读代码判断。如果它们先于功能存在，静默降级与不可达路径会在开发当天暴露，而不是在审计当天。

**任何策略的执行点都必须在对手改不动的那一侧。** 应用在服务端校验，客户端只做呈现。IP 白名单的全部返工都源于违反这一条：先在头部画了一个字段，后来才发现「写在谁那里」和「由谁执行」是两件事。

**不要在没有测量手段时给安全功能下结论。** IP 白名单改完之后，`ConnectInfo` 在真实远端、NAT 或代理之后给出哪个地址只能靠部署一次去观察。与其在文档里含糊其辞，不如把实测结果（转发拓扑下看到的是 `172.17.0.1`）直接写进安全边界一节；每一个安全断言也应配一个会在它不成立时失败的程序。

**把「文档说 X」当成对代码的缺陷报告。** 在证明代码确实如此之前，默认文档是错的——本项目里文档漂移是数量最多的一类缺陷，且全部朝着夸大能力的方向。

**验证一个否定结论之前，先验证检测手段。** 发布页的 0 个产物与 Windows 上永不失败的端口测试，都是检测手段出错被读成功能故障。

## 6. 方法上的收获

真正抓到问题的，都不是「多写几个断言」，而是几个可复用的做法。

**主动寻找非预期输入的测试。** `tests/robustness_test.rs`（作为 cargo-fuzz 的确定性替代）在引入后的**第一次运行**就抓到了产物头部解析越界 panic：`PackHeader::from_bytes` 用文件内读出的长度字段直接切片，而此前只校验了固定的 32 字节尾字段，被截断或长度字段被伪造的产物会让程序 panic 而不是返回错误。对一个专门解析不可信输入的工具来说这是实打实的缺陷。

**逐 crate 的依赖审计。** 结果是一次就清掉了 10 个声明了但源码零引用的依赖（核心库 4 个 `hkdf`、`flate2`、`anyhow`、`tracing`，服务端 2 个 `sha2`、`tracing`，图形界面 4 个 `egui_extras`、`anyhow`、`tracing`、`uuid`）；其中一个 `anyhow` 移除后彻底离开了依赖树，连带暴露了 [ATTRIBUTION.md](../ATTRIBUTION.md) 里的虚报条目。同一轮审计还纠正了 README 里「`testdata/` 未被引用」这句等于在首页承认有死目录的描述。

**「声明 vs 实现」审计。** 按 `path:line` 逐条对照 `PackConfig` 每个字段与文档里的每项能力，结论不软化。它得出的结论——已交付的是被描述产品的很小一部分——是这份复盘的起点。它的价值不在于发现了几个 bug，而在于把「文档承诺」与「代码事实」变成同一张可核对的表。

**端到端服务端测试。** 不再依赖人工 curl：用 `CARGO_BIN_EXE_secunzip-server` 拉起真实服务端进程、用 `std::net::TcpStream` 手写 HTTP 请求（不引入 HTTP 客户端依赖），覆盖鉴权、注册防覆盖、多应用隔离、迁移与审计保留、备份、启动失败路径与健康检查。加超时的 `run_bin` helper 同时消除了整个测试文件永久挂起的可能。这类测试是唯一能证明「安全逻辑真的在服务端」的东西。

**跑真实部署，而不是相信本地绿构建。** 在软路由容器里实际部署服务端、连真实数据库、经历一次从 schema v1 到 v2 的迁移。这一轮暴露了本地构建永远看不到的东西：看护循环不可靠、`pkill -f` 自伤，以及白名单在 TCP 转发拓扑下看到的是 `172.17.0.1` 而不是真实客户端地址——最后一条直接改变了功能的实际定位，被写进 [docs/design.md](design.md) §7 与 README 的说明里。本地绿构建会让人相信这些都没问题。

**审计信息本身的来源也要防止出错。** 这一轮里有两处必须纠正的推理错误：一处是把审计摘要里列举的 `KeyNode` 流程求值点当成了 CLI 打包路径，实际那里只是随机 UUID 生成 `content_key`（CLI 打包直接写死 `Literal`，根本没有流程）；另一处是把 `KeyNode::Conditional` 记成「全仓库无构造点」，而测试里构造了它，即条件分支仅测试可达。**结论不软化，但摘要也必须回到证据**——这正是要求每条结论都带 `path:line` 的理由：当摘要与证据冲突时，能立刻判出是摘要错了。

## 7. 材料中的矛盾与未确认项

写这份复盘时，以下几条在材料里无法互相印证，如实留在这里，不替它们圆场：

- **[README.md](../README.md) 与 [docs/release.md](release.md) 曾写着发布流程「尚未实跑验证」**，与仓库里已发布的 `v0.1.0` 至 `v0.1.3` 四个 tag 不符。这是方向相反的文档漂移（文档比实现更保守），在本文写完后已一并订正为实跑结果。
- **未引用依赖的数量曾有两个口径**（提交记录 10 个、缺陷记录 12 个）。复核那次提交的实际内容后确认是 10 条依赖声明（核心库 4、服务端 2、图形界面 4），缺陷记录里的 12 是笔误，已一并订正。
- **`assets/runtime_stub.exe` 只有 11 字节**，它是 `current_exe()` 读取失败时的回退；文件保留是刻意的（打包时占位必须存在），但它能否作为 runner 运行未经验证。
- **若干路径只有代码推理、没有实测**：黑盒 EXE 的真实双击行为（需要交互桌面会话）、`net use` 的成功与失败路径（在自动化测试里创建盘符映射会污染使用者的机器，这是刻意的取舍）、非 Windows 分支的编译验证，以及 GUI 的运行时渲染。
- **审计的边界**：[docs/design.md](design.md)、[README.md](../README.md) 与 [CHANGELOG.md](../CHANGELOG.md) 都声明本项目是课程作业、未做安全审计与渗透测试，交付后不再维护。复盘本身也不是安全评估，它只对照了「声明」与「实现」。
